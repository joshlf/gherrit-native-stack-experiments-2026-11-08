# Independent evidence audit

Read-only audit of `race-results.json`, `structure-results.json`, their harnesses, retained HTTP responses and local Git objects on November 8, 2026. No remote operation was performed for this audit. The evidence supports several useful traces, but the race suite is not six uniformly passing controls. One result is a harness error; several conclusions require narrower wording than their case names suggest.

## Races and response matching

- **Atomic Git:** independently confirmed that the rejected atomic push left the entire observed ref vector unchanged. Its lease for existing B deliberately expected absence. The corresponding non-atomic control returned failure while A and both v2 archive refs moved and B stayed old. The archive for B's proposed revision therefore existed before B's head published. The explicit repair subsequently moved B. These observations support the recorded ref-transaction distinction, not atomicity of PR or membership operations. Sources: `evidence/atomic-stale-rejected.push.json`, `evidence/nonatomic-control.result.json`, and the three snapshots embedded in `race-results.json`.
- **Selected head and 409:** the original request selected B=`f1daa6ba...` with squash. A competing rebase request returned HTTP 409 naming the **same original UUID** `b851e479-a2b1-4ed5-9e2b-85b627e17955`, original squash options and original selected SHA. It did not accept the requested rebase intent. The harness correctly polled the original receipt. Its generic `poll_merge` function contains a three-field conflict guard, but this test did not invoke that guard on the conflicting response; it is source inspection, not an exercised conflict-rejection check. The tested request bodies contain only method, action and selected SHA. Optional commit-message fields and genuinely lost responses were not tested.
- **Selected-head outcome:** the branch push to B=`538d3298...` completed at 23:22:47.682Z. The original request nevertheless reached `merged`; PR #69 later reported that new branch head. Independently inspecting landed trunk `657933ba...` shows `race-selected/B.txt` is **`B=1`**, the original selected content, whereas the pushed replacement is `B=2`. This demonstrates landing the accepted old revision while the branch advances. It does not demonstrate a continuing live-head fence, rejection of the changed head, or landing the new content. Internal server ordering is not exposed by these timestamps. Sources: `evidence/race-selected-request.meta.json`, `race-selected-different-options.meta.json`, `race-selected-head-change.push.json`, `race-selected-after.snapshot.json`, and the retained Git object.
- **Unselected downstack change:** the aggregate contains an `error`, not a passing result. Raw poll 1 returned terminal `failed` with “merge conflict”; the after snapshot shows all three PRs open and the trunk unchanged. The subsequent unconditional `git show <unchanged-trunk>:race-downstack/A.txt` failed because that path was never landed. This is an oracle/control-flow error after a meaningful provider rejection. Do not report a successful changed-downstack landing or a vector-lease guarantee. Sources: `evidence/race-downstack-result-poll-1.meta.json`, `race-downstack-after.snapshot.json`, and `run_races.py`'s `downstack_change`.
- **Unstack overlap and closed middle:** unstack returned 204 while a merge request was pending; its receipt then failed because the PR was no longer stacked, with all observed refs unchanged. A separate upper-prefix attempt with a closed middle PR failed the open/non-draft requirement, with no observed partial landing; reopening the middle PR returned 200. These are particular observed orderings. They do not establish cancellation or eligibility behavior for every pending or queued operation.

For the decisive statuses above, I reparsed the saved HTTP response files and confirmed their status/body match the `.meta.json` records. There was no induced lost-response recovery test **in the audited race/structure suites**. A separate, later `run_lost_receipts.py` hosted-fault probe is outside this audit; its child-process interruption should be distinguished from an actual network timeout. The race harness's `fresh=True` creates a newly recorded GET rather than reusing a local receipt; it does not add a cache-control header or make the read an authoritative transaction snapshot.

## Structural operations

The five deliberate transitions—reorder, insertion, drop, fold and trunk change—match the actual returned stack order. Existing retained PR node IDs match their previous snapshots, active head SHAs match refs, the intended PRs remain open/unmerged, and every previously recorded archive tag retains its target. I also checked all 17 `structure*.commit.json` input SHAs against their local `refs/experiment-inputs/` pins. The aggregate's retention flag is therefore supported for these enumerated inputs and archives. A newly created D has no prior review identity to preserve.

These operations **unstack, park, push, set final PR bases, and register**, creating successive groups #50 → #51 → #53 → #54 → #55 → #56. They do not exercise an in-place native membership-edit API or an atomic cross-resource transaction. The fixture has no reviews or pending native merges, so it does not validate approval retention or structural edits overlapping provider work. Dropped D and folded A were explicitly closed unmerged and retained; closed PRs were not all retargeted during the later trunk change.

The unparked reorder control is stronger than a generic “closed PR” description: B #58 became **closed with `merged: true`** when rewritten A contained it, while the intended trunk stayed unchanged. The attempted base repair and reopen both returned 422. This is an observed GitHub lifecycle consequence of containment in its direct base, not evidence that the intended trunk landed B. Sources: `evidence/unsafe-after-heads-0.snapshot.json`, `unsafe-repair-base.response.txt`, and `unsafe-reopen-control.response.txt`.

The `completed-extension` case begins with group #28 already **open**, containing unmerged D #29. Its append-E 200 therefore tests extension of that active historical group; evidence for the earlier append to a fully completed group belongs to `basic-results.json`, not this case alone. Here, merging D left E eligible; unstack returned 200 and retained four merged members. E #30 was released, new F #60 was created, and E/F registered as group #61. The final `eligible: [E, F]` includes newly created F; it does not mean both PRs were released from the old group.

## Observer and finite sampling

The required-status failure returned terminal `failed`, with all PRs open and the observed ref vector unchanged. The positive phase released C's failing status while retaining the protection rule. That supports this all-prefix admission control.

`evidence/observer-detailed-samples.json` contains **16 overlapping read cohorts**. Endpoint intervals span 23:24:14.651583–23:24:28.784084Z, about **14.13 seconds**; the reported 16.77-second harness elapsed time also includes later work. The first terminal poll spans 23:24:22.593665–22.816768Z. Later endpoint coverage extends only about **5.97 seconds** beyond that response. The `refs_at` timestamp precedes each `ls-remote` invocation; its completion time is not recorded.

In cohort 8, D's GET returned old head `e6551ba6...`, while the subsequent ref read returned rewritten `c65becf7...`. That GET overlaps the terminal poll, so the trace demonstrates **cross-resource observation mismatch**, not proof that a suffix write occurred after the terminal response. Cohort 9 reports the matching new PR head. The already merged A's historical `base.sha` differing from the current trunk is not an active-head inconsistency.

PR lifecycle responses progress through A-only, A/B and A/B/C marked merged while the sampled trunk already points to final `19e963db...`. This does not prove non-atomic Git landing; per-PR metadata observations are separate from the branch-ref update. The fresh disjoint ref remained `ef296b45...` in every sample, which supports bounded noninterference for that ref only. Neither matching later reads, terminal status nor this stable interval establishes a future-write settlement guarantee.
